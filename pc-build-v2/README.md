# CR Tools V2

Isolated M7 release-capable client for the Windows-only CR Tools V2 application. This package does
not reuse V1 implementation code and has a separate development and packaging
identity:

- package: `cr-tools-v2`
- product: `CR Tools V2`
- application ID: `com.snipe.client.v2`
- artifact: `CR_Tools_V2_Setup_${version}.exe`

## Commands

For a local Windows installer, run `..\publish-update.cmd test`. After reviewed
changes are merged to clean, synchronized `main`, run `..\publish-update.cmd release`
to build on your own PC and publish an update for installed clients. GitHub only
signs and deploys that exact finished installer; it does not build it again.
See [the local Windows publisher runbook](docs/RELEASE_RUNBOOK.md#local-windows-publisher).

Requires Node.js `^20.19.0` or `>=22.12.0` and npm. Windows release packaging also
requires PowerShell 7 (`pwsh`).

```bash
npm ci
npm run dev
npm run typecheck
npm run lint
npm test
npm run build:app
npm run build:unpacked
npm run build
npm run test:e2e:windows
```

`build:app` creates the electron-vite application bundles without an installer.
The `build:unpacked` and `build` commands target Windows x64 and require the pinned
portable runtime generated by `npm run runtime:build`. The runtime, NSIS, and Playwright
steps are Windows release gates and are not simulated on Linux.

## Architecture

- `electron/main/application`: explicit application lifecycle and composition.
- `electron/main/windows`: the only `BrowserWindow` registry and sender authority.
- `electron/main/ipc`: narrow handlers with sender, URL, payload, and result checks.
- `electron/main/infrastructure`: fixed production server config, encrypted secrets,
  redacted logging, and versioned settings.
- `electron/main/services`: bounded HTTP/OCR and card assets, Windows device identity,
  auth session, generation-fenced WebSocket/setup/monitor state machines, local-widget
  controller, source resolver, owned child-process supervisors, and one custom updater.
- `electron/main/domain`: internal-only capture selectors; renderer DTOs never contain
  Electron source IDs, HWNDs, process IDs, monitor indices, or executable paths.
- `python`: framed one-shot capture and trigger analysis workers plus a strict persistent
  JSON-lines monitor, pinned to `windows-capture==2.0.0`.
- `electron/preload`: independent main, auth, and widget entry points; setup is a narrow main namespace.
- `shared/contracts`: Zod IPC contracts shared by main and preload.
- `shared/models` and `shared/errors`: boundary-safe models and errors.
- `renderer`: separate sandboxed auth, main, and widget React entries with restrictive
  CSPs; the full-window setup editor is hosted by main.

The renderer has no Node.js integration, filesystem access, tokens, full HWID,
generic IPC, or generic settings API. Auth and main windows expose separate narrow
preload APIs. Every call is runtime-validated on both sides, and main verifies the
sender WebContents ID and renderer URL through the one window registry.

Settings use strict Zod schemas and atomic `userData/settings.v2.json` writes.
The v1 settings file remains rollback input. Defaults enable automatic monitoring,
close-to-tray and opponent notifications; Windows login startup and diagnostics stay
disabled. Typed patches are serialized so concurrent updates do not replace unrelated
fields; explicit undefined values are rejected. Login-item launches carry
`--launch-in-tray` only through the initial bootstrap, then consume that hidden-start intent.
Later user-driven logout/login transitions show auth/main; ordinary launches show main.
The native tray offers status, start/stop, profile switching, overlay show/lock,
restore and Exit. User close hides the window while monitoring continues; Exit,
updates and Windows session shutdown bypass hiding. Main bounds/maximized state use
the separate `userData/main-window-bounds.v1.json` file.
Saved maximization is deferred until first show for a hidden launch, and an unpositioned
main window centres on the primary display. `query-session-end` flushes pending
bounds/journal/log writes without stopping monitoring; only `session-end` commits to shutdown.

Local widget settings are strict per-user atomic files under
`userData/widget-settings.v3/`, importing v2 without deleting it. Defaults enable
auto-open and always-on-top and use normal width 360. Compact mode starts at width 520
and restores the saved normal width on exit. Width-derived scale is
`clamp(width/360, 0.86, 1.5)`, never an independently persisted value. Compact minimum
width is 440; minimum height is 80 rather than the obsolete 280. Native bounds are
clamped to current work areas, including when a display is smaller than those minima.
Position and size are saved after user move/resize events.

M0 service readiness loads the authenticated user's widget settings before opening
the main renderer. A failed load keeps authentication visible rather than inventing
settings. Logout/user switches fence pending loads. Monitor stderr is drained as
rate-limited diagnostic counters and never terminates capture by lifetime volume;
stdout remains a strict protocol. Metadata helper failures are reported separately
from absent/ambiguous sources, without relaxing exact identity matching.
Individual unverifiable windows remain disabled; a bound window that closes during
metadata lookup is not-found. A display-helper failure leaves windows in the picker
and disables unverifiable displays. Recovery never relaxes exact title/executable
identity or calibrated fixed-ROI matching.

Sanitized asynchronous diagnostics rotate under `userData/logs` (five files of at
most 1 MiB each, bounded pending writes). Disk failures do not stop monitoring.
The old Settings screen's “Открыть папку логов” action uses the main-only
`openLogFolder` capability for that fixed directory; it accepts no path. Dropped
records and failed writes are counted and summarized when the disk next accepts
records or at shutdown. Diagnostics never contain raw worker stderr, exception messages/stacks,
private images, title/nickname/email fields or credential-bearing URLs.
Account additions return typed error codes or a saved-with-warning result; old
servers without codes receive an honest generic message, not a guessed cause.
Allowlisted save failures (`ACCOUNT_SAVE_UNAVAILABLE`) report that saving failed
and can be retried later, distinct from game API outages. Codes, not HTTP status,
identify account causes; raw server responses never reach the old form's messages.

Capture configuration is separate and per server user under
`userData/capture-profiles.v4/` (collection schema 3, configuration schema 2).
It separates private `SourceBinding` identity from `LayoutCalibration`, with semantic
nickname/evidence/trigger regions, structural templates, revision and fingerprint.
V3 collection and legacy single-config imports preserve IDs, names, timestamps,
active profile, geometry and template quality; old files remain untouched. Imports
have unknown viewport/layout and null whole-layout confidence, not fabricated
automatic-calibration quality. Prediction result references migrate only from the
exact validated old profile revision/fingerprint. No migration contacts the server.
There are no screenshots, RGB templates, tokens or full executable paths on disk.
A saved HWND is a private binding hint, never a renderer source identifier.
Setup atomically saves the canonical local model before posting its schema-version 2
`/api/user/me/ocr-regions` compatibility projection. Its view reports local persistence,
server synchronization, and runtime restart independently; a failed projection can be retried
without saving again, provided the session, authentication, profile, and fingerprint still match.

The production origin is fixed to `https://api.artcsworld.xyz`; realtime uses
`wss://api.artcsworld.xyz/ws`. The refresh token is encrypted with Electron
`safeStorage` and written atomically to `userData/auth.v1.enc.json`. Access tokens
remain memory-only. If platform encryption is unavailable, authentication fails
closed and no plaintext fallback is written. Logout posts the bounded refresh token to
the fixed `/api/auth/logout` revocation endpoint, then always performs durable local
invalidation; network revocation failure cannot skip local cleanup.

Production HWID generation is Windows-only and uses one non-shell PowerShell/CIM
invocation. Non-production Linux development uses an explicitly constructed dev
provider and cannot silently instantiate the Windows production identity.

## Capture Setup

M3 implementation is complete. The Capture workspace explicitly enumerates Electron
window/display sources, uses opaque short-lived keys, and creates bounded lazy previews.
Starting setup captures the canonical frame before entering the main window's full-window
editor. The editor maps pointer and numeric coordinates through a letterboxed contain transform
and stages Trigger, Normal, and Precise regions before analysis/review/commit.

Install the Python environment on Windows with Python 3.10 or newer:

```powershell
py -m venv .venv
.venv\Scripts\python -m pip install -r python\requirements.txt
$env:CR_TOOLS_PYTHON_PATH = "$PWD\.venv\Scripts\python.exe"
npm run dev
```

`npm.cmd run test:python` always uses this worktree's `.venv`, never a global
pytest. It creates the isolated environment if missing and installs the pinned
capture requirements plus pytest when test dependencies are missing, then runs
the suite. First-time setup requires Python 3.10+ on PATH and package-download
access; subsequent runs use the existing local environment without installation.

Production packaging includes a managed interpreter at
`resources/python-runtime/python.exe`. `scripts/Build-PortablePython.ps1` downloads the
pinned NuGet Python 3.11.9 package on Windows, installs only pinned wheels, runs `pip check`
and import smoke tests, removes caches/tests/bytecode where safe, and preserves discovered
license files. `scripts/New-RuntimeInventory.ps1` writes the bundled relative-path,
size, and SHA-256 inventory. The application never downloads Python at runtime. There is
no fake Linux runtime or alternate screenshot backend.

Display capture maps Electron displays to Windows device names only when a fixed,
per-monitor-aware PowerShell helper returns a unique exact physical-bounds match. Missing,
duplicate, or mismatched data remains unsupported rather than guessing monitor order.
Window capture uses a validated signed-64-bit decimal HWND with `window_hwnd`.

## Monitor And Results

Monitoring auto-starts once per authenticated user per process launch when an active
configuration exists and the setting is enabled. Auto-start is detached, generation-fenced
and logged independently of auth/window synchronization. Start performs auth, per-user
preference, calibration and exact durable-source preflight before spawning one owned
Python worker. Missing/closed/unavailable or ambiguous sources enter `WAITING_SOURCE`
with run intent retained; bounded 1/2/5/10/15-second resolution backoff can resume only
the unchanged saved binding/calibration. Unknown executable identity fails with
`SOURCE_REBIND_REQUIRED`, never title-only recovery or endless source waiting. Such
imports retain their provenance but need validation; profiles and the old renderer explicitly
require rebinding. Profile health uses one shared native source/metadata snapshot per view,
retaining window health if only display metadata fails. Stop, auth change, active profile
deletion and Exit cancel recovery; ambiguity never selects an arbitrary source.

Monitor preferences are strict per-user atomic files under
`userData/monitor-preferences.v2/` with deck mode `pol` by default. The v1 importer
keeps deck mode and drops search mode. Deck mode can change while monitoring for the
next captured attempt; an in-flight attempt and its manual retry keep their original
parameters. Renderer views contain no tokens, HWNDs, selectors, trigger templates,
source images or raw OCR/model responses.

The private monitor protocol is JSON-lines version 3. Main sends one validated start
command and an eventual stop command. Python emits monotonic, session-bound `ready`,
`triggered`, `action`, prediction, diagnostic, `fatal` and `stopped` events with trigger IDs.
Action PNG base64 exists only on the private pipe and is decoded immediately in main,
never logged or sent to a renderer. Worker readiness
has a 15-second deadline, allowing the worker's 7-second no-frame deadline plus
an 8-second cold-start margin; stop is graceful first and then uses Windows process-tree
termination. Stdout lines, stderr diagnostics, image dimensions/bytes, event ordering, and
session generations are bounded and validated.

The local Trigger V3 engine checks color-independent structural maps at 10 FPS and uses
bounded edge/orientation correlation with ORB alignment only when the analyzed template
supports it. Setup also generates a transient V1 grayscale projection using V1's actual
hex-character aHash distance semantics; it rejects selections without enough luminance
contrast to be safe in V1. Trigger rectangles are canonicalized to source pixels before
analysis and persistence. The monitor uses the fixed saved trigger ROI and crops the
nickname region from the same confirmation frame. There is no 2.2-second delay,
fast/precise runtime branch, whole-frame trigger scan or automatic second search.
Both calibrated data regions remain available in the canonical model. OCR uses only
`POST https://api.artcsworld.xyz/api/ocr/process`, a 150-second deadline, owner
cancellation, and one auth refresh after 401. Player found, player not found, recognition
failure, service/network failure, and blocked auth remain distinct.

The HTTP compatibility adapter sends `search_mode=fast`. Search progress pushes
trigger/attempt/profile/calibration IDs and capturing/requesting/completed/failed phase.
Only retryable, non-auth service failures retain one crop in RAM (maximum 10 MiB,
120 seconds); manual retry coalesces clicks, uses the original parameters, and counts
each actual request. New triggers, source loss, Stop, auth changes and expiry release it.
The old renderer remains supported by the narrow contracts; the new UI consumes these
views rather than inspecting capture identity or private process state.

Sessions retain their ID through source waiting and safe runtime restarts. Duration
includes waiting, and Stop/Exit finalizes and flushes a summary once. Repeat counts
use canonical player tags, never nicknames; the current-session count is independent
of earlier-today repeat marks. “Today” is the OS-local calendar day across sessions.
The journal retains at most 2,000 results, 40,000 minimal encounter index entries and
100 summaries for seven OS-local calendar days including today, cut off at midnight six
dates before today; the renderer's latest 20 results are only a view cap.
Re-delivery of a known result/trigger replaces that encounter instead of creating
another meeting. History storage errors are visible but do not disable capture.
Invalid records are dropped independently on load without rewriting the source. A failed
non-ENOENT read/root validation blocks disk saves and keeps new records memory-only,
including on Stop/Exit; the next view/history request retries and merges memory with disk
after a successful load. Save failures are reported after publishing the result.
Private crops/screenshots are never journaled.
Legacy `ocr_reprocessed` events have no structured server correlation and are kept as
standalone entries marked `reprocessed`, visible in history and the overlay. They
never affect session counters, the repeat-encounter index or the session summary.
No nickname guessing or server changes are used to merge them.

Development source execution uses `python/monitor_engine.py`. Production packages include
the managed Python runtime and verify its bounded size/SHA-256 inventory before the first
Python spawn. Linux does not simulate a successful capture; only pure protocol, algorithm,
process, OCR, and supervisor tests are cross-platform.

## Local Widget

M5 is implemented. Starting monitoring from the main window immediately opens the dedicated
widget with an empty deck placeholder while capture is being prepared. `WidgetController`
owns one generation-safe monitor result subscription and also opens the widget for a new
`player_found` result when auto-open is enabled. Opening the widget clearly shows empty, not-found, recognition-failure,
or service-error state. Closing the widget never quits the application; logout and auth
loss close it.

`WindowCoordinator` remains the only `BrowserWindow` registry. The widget has a dedicated
sandboxed preload and renderer entry, production devtools disabled, blocked navigation and
popups, and a CSP with `connect-src 'none'`. Its preload exposes validated view events with
fallback polling, indexed
card asset lookup, allowed settings updates, and hide. The view strips card URLs and never
contains tokens, capture selectors, raw OCR responses, or screenshots.

Card images are optional. `ImageAssetService` resolves result/deck/card indices against a
currently retained monitor result and only accepts exact HTTPS host
`api-assets.clashroyale.com`. It performs manual redirect validation, a five-second
timeout, 512 KiB response limit, PNG/JPEG/WebP signature and dimension checks, sends no
credentials or referrer, stores a bounded in-memory LRU, and keeps validated assets in a
content-addressed disk cache. The cache is warmed from the server card manifest in the
background, including normal, evolution, and hero variants. Any failure displays card initials
and name. Renderers cannot provide an asset URL or perform direct HTTP requests.

Widget controls are keyboard-focusable and labeled: pin, position lock, compact mode,
opacity, deck tabs, and hide. The Settings page exposes the same behavior and honestly
also owns manual update check, download, cancellation, and install controls.

## Streamer Workspace

M6 is implemented for the active V1 parity scope. The tabbed Streamer workspace supports
Twitch connect/status/disconnect, automatic predictions, result-region calibration, automatic
stream titles and Clash accounts, deck sharing, and adaptive OBS opponent/stats overlays.
Alerts, Discord, the old generic OBS placeholder, and `smart_predictions` are intentionally not
ported.

All streamer management requests originate in main through an authenticated API seam that keeps
the app JWT memory-only and retries once after a 401 refresh. The renderer receives one strict,
bounded `StreamerView`; Twitch credentials, widget tokens, complete OBS URLs, screenshots, raw
server payloads, and model output do not cross preload. OBS URLs can only be copied by a typed
`stats`/`opponent` command. OBS renderer preview URLs use the existing fixed-origin, token-free
public preview route; bearer URLs and token rotation stay in main.

OAuth opens only a server-returned HTTPS URL whose exact host is `id.twitch.tv`, using Electron's
system-browser `shell.openExternal`. The callback remains server-owned, and main performs bounded,
non-overlapping status polling while the Streamer page is active or a connection attempt is
pending. No remote `BrowserWindow` or `window.open` is used.

Prediction preferences and result profiles are strict per-user atomic files under
`userData/prediction-preferences.v1/` and `userData/prediction-result-config.v1/`. Result setup
resolves the explicitly selected capture profile (including inactive profiles) and edits a real
captured result frame in the same main-window setup namespace. Result geometry is saved locally
first. Only an active profile updates the server's legacy mirror, in trigger/data order; those
two endpoints are not transactional. A partial remote failure is a synchronization warning,
not a false local-save failure, and the same fenced retry resends the saved mirror.

Predictions reuse the single monitor process. Normal battle triggers notify the server through a
serialized main-only coordinator. The optional result profile has one confirmation and a 60-second
cooldown; its cropped PNG is emitted on the private process pipe and posted as multipart with a
150-second deadline, never exposed to a renderer. Start rolls the server back if local monitor
configuration fails. Stop removes prediction runtime while preserving a monitor that was already
running.

Known server limitations are not hidden by client fallbacks. The OAuth state now uses one-time,
expiring server records, but the previously exposed Twitch client secret must still be rotated.
V2 also keeps the system-browser flow outside Electron. OBS URLs remain bearer capabilities under
the server's widget-token model; rotating the token invalidates existing browser sources.

## Updates And Releases

M7 implements exactly one custom updater; `electron-updater` is not installed. It runs only
in packaged Windows builds. Development and non-Windows builds report that updating is
unsupported instead of simulating success. Startup performs a delayed check only and never
downloads or installs automatically.

The fixed manifest is
`https://updates.artcsworld.xyz/downloads/v2/manifest.json`. Main accepts only strict schema
version 1, verifies its canonical payload with Ed25519, and then permits only an exact
`https://updates.artcsworld.xyz/downloads/v2/CR_Tools_V2_Setup_<x.y.z>.exe` artifact.
Redirects remain on that origin/path, downloads are bounded and atomic, and size plus SHA-512
are verified before READY and again immediately before launch. The renderer never receives a
URL, signature, hash, or filesystem path.

Both the authenticated main renderer and the unauthenticated auth renderer receive only the five
typed update commands. This lets a user install a login-compatibility update without exposing the
main preload surface. After a newer manifest's installer is downloaded and passes exact size and
SHA-512 checks, the client atomically persists its highest trusted version and complete manifest
digest. It rejects lower versions or changed signed metadata for that version on the same
installation.

Schema version 1 remains unchanged so already-built 0.1.18 clients can consume the next release.
The local version floor and monotonic deployment checks reduce replay risk, but they are not a
complete anti-replay protocol: a fresh or reset client has no local history, and schema v1 has no
signed expiry or sequence. Those properties require a staged future schema migration after a
transition client that understands both schemas has been deployed through schema v1.

The checked production public key is `resources/update-public-key.pem`. Its SHA-256 SPKI
fingerprint is `8be2a82e869112c3d67de63f0f60ee0d6beb057eb9b160d8effad92098a60b0d`.
Manifest signing is not Authenticode. By product decision, releases have no Windows
Authenticode certificate, so SmartScreen can show an unavoidable "Unknown publisher" warning.
Neither the Ed25519 manifest nor electron-builder executable resource editing would remove
that warning.

After changing V2 code, run `./publish-update.sh`. It selects or reuses the release version, runs
all gates, stages only the V2 allowlist, commits, securely pushes `main`, dispatches the correlated
Windows workflow, and downloads the verified result. Release mode signs and publishes only after
the explicit `PUBLISH` confirmation. GitHub artifacts expire after one day; durable installers and
the manifest stay on the existing update server. See `docs/RELEASE_RUNBOOK.md` for key rotation,
artifact verification, deployment, and rollback procedures.

## M3–M5 UI Contracts

The main window is frameless (default 1100×700, minimum 420×360); auth defaults to 480×640.
`crTools.window.command()` accepts only `get`, `minimize`, `maximize`, `restore`, and `close`.
Close uses the native close event and the existing close-to-tray policy, never a direct destroy.
Setup start does not create another window. `crTools.setup` exposes strict session/generation
commands, selected-profile result setup, and saved-projection retry; auth and widget cannot invoke it.

`crTools.streamer.command()` is the single typed mutation boundary for Twitch, predictions,
title settings/preview/apply/undo, chat, OBS widgets, and accounts. Its allowlisted errors preserve
M0 account codes; successful committed mutations can carry `TITLE_UPDATE_FAILED` or
`REFRESH_FAILED`. `getReadiness()` projects Twitch, enabled account count, running-monitor
readiness, capture presence, and the active capture/result association in main. Unknown or
unavailable sections are null, not disconnected.
Title presets/chips compile to the existing server template/include/account-selection fields.
Decompilation preserves arbitrary existing templates through explicit raw mode. There is only
one `{account}` token: active-account and best-account chips cannot be promised simultaneously.
The existing title endpoint acknowledges settings, not a distinct Twitch application receipt:
explicit apply returns `unconfirmed` plus `TITLE_APPLICATION_UNCONFIRMED`; the known saved-but-
Twitch-failed response returns saved success with a warning, while an unrelated gateway failure
remains an error. Undo uses the existing real server undo operation.
The allowlisted stable server code `TITLE_SAVED_APPLY_FAILED`, when present, is accepted
on title settings/enabled/pause; the exact existing localized message remains the fallback.
The server rollout of that code is a follow-up, not a server change in this client task.

`crTools.h2h.lookup({ requestId, opponentTag, recentLimit })` calls authenticated
`GET /api/user/me/h2h`. Server statuses `ok`, `none`, `unavailable`, and `no_accounts` remain
distinct. A missing endpoint is `unsupported`, never `none`; HTTP 429 exposes a retry timestamp
and prevents another request until it expires. Lookups coalesce by canonical tag/limit/user
generation, support per-request cancellation, and are cancelled on auth change or main destruction.
Coverage is only recorded Path of Legends history, not proof that a player exists or has no history.
No-account and not-found states are never inferred from transport errors.
The HTTP parser strips additive fields, including nested objects, then projects into strict
IPC. Real `stale` and `coverage.complete` booleans are preserved. Non-H2H 429 responses
retain bounded error bodies/messages and attach Retry-After metadata.
Unknown future HTTP `status` or `reasonCode` strings normalize to `unavailable` with the
allowlisted `H2H_SERVICE_UNAVAILABLE` capability error; they never leak into strict IPC.

Main and widget have only canonical player-tag clipboard commands, not arbitrary clipboard writes.
Widget settings accept bounded `contentHeight` (80–720), not arbitrary native bounds; normal and
compact widths remain separately persisted. OBS bearer URLs, JWTs, raw API envelopes, HWNDs, and
capture selectors never cross these bridges. The existing update view already supplies version,
release notes, download progress, ready/error state and verified install; no second updater was added.
Widget views include the public `monitorError` (null when absent). Identity rebinding is
projected as «Выберите окно игры заново в профиле» in monitor errors and the native tray.
Session-query and shutdown flushing share one in-flight promise; a settled query can be
flushed again later if Windows cancels logoff and the user continues working.

Legacy v2 widget settings that fail JSON/schema validation return defaults without changing
the old file. Invalid/unreadable optional legacy prediction-result geometry is left unattached
and logs only the error type; it does not invalidate the capture-profile migration. Nickname
confirmation/action share their trigger UUID, while `prediction_result` has an independent
event UUID and must not be correlated by it.
